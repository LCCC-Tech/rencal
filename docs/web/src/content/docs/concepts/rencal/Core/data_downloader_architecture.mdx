# Data Downloader Architecture

The [`rencal.core.data_downloader` module](/reference/rencal/core/rencalcoredata_downloader/) is responsible for acquiring source datasets used by RenCal calibration and simulation workflows.

Where the [Data Loader Architecture](/concepts/rencal/core/data_loader_architecture/) focuses on reading local artifacts into validated models, the downloader layer is responsible for creating those local artifacts in the first place.

## Why this module exists

RenCal depends on multiple external data providers with different protocols and formats:

- **Copernicus CDS API** for ERA5 weather (`.nc`),
- **LCCC APIs/CSV** for CfD register and BMU mapping (`.csv`),
- **Elexon BMRS API** for generation settlement data (JSON -> parquet).

`data_downloader.py` centralises this acquisition logic behind shared abstractions so ingestion remains reproducible and easier to operate.

## Core abstraction: [`DataDownloader`](/reference/rencal/core/rencalcoredata_downloader/#datadownloader)

[`DataDownloader`](/reference/rencal/core/rencalcoredata_downloader/#datadownloader) is an abstract base class that provides:

- a shared output root (`DOWNLOAD_DATA_DIR`),
- `_update_output_directory(...)` for source-specific subfolders (see [`DataDownloader`](/reference/rencal/core/rencalcoredata_downloader/#datadownloader)),
- a required [`download()`](/reference/rencal/core/rencalcoredata_downloader/#datadownloaderdownload) method for concrete implementations.

This creates a consistent contract across all external data download flows.

## Concrete downloaders

### [`ERA5DataDownloader`](/reference/rencal/core/rencalcoredata_downloader/#era5datadownloader)

Responsibilities:

- determine download years from `CALIBRATION_START_DATE` and `CALIBRATION_END_DATE`,
- authenticate with CDS (`cdsapi.Client`) using env/config,
- request wind and solar variables separately, then merge to a single yearly NetCDF,
- verify file structure and annotate metadata,
- skip or verify existing historical files while refreshing current-year outputs.

Notable reliability mechanisms:

- lazy CDS client initialization with explicit error messages for missing API key,
- per-year verification via `_verify_and_update_metadata(...)` on [`ERA5DataDownloader`](/reference/rencal/core/rencalcoredata_downloader/#era5datadownloader),
- progress visibility via `tqdm`.

### [`CfDDataDownloader`](/reference/rencal/core/rencalcoredata_downloader/#cfddatadownloader)

Responsibilities:

- download CfD register data,
- download CfD-to-BMU mapping CSV,
- normalise key fields and merge datasets,
- persist plant-level output to `plant/{PLANT_DATA_FILE_NAME}`.

This dataset is a dependency for generation downloads and for plant-level model ingestion.

### [`GenerationDataDownloader`](/reference/rencal/core/rencalcoredata_downloader/#generationdatadownloader)

Responsibilities:

- load locally saved CfD/BMU data to determine relevant BMU IDs,
- request settled generation data from Elexon over calibration window,
- map settlement periods to hourly UTC timestamps,
- handle daylight-saving edge cases (normal/short/long settlement days),
- allocate shared BMU generation proportionally to plant capacity,
- aggregate to plant-level hourly quantities and save parquet.

This stage converts operational market settlement records into model-ready time series.

## Orchestration: [`DownloadManager`](/reference/rencal/core/rencalcoredata_downloader/#downloadmanager)

[`DownloadManager`](/reference/rencal/core/rencalcoredata_downloader/#downloadmanager) composes the three concrete downloaders and exposes:

- [`download_cfd()`](/reference/rencal/core/rencalcoredata_downloader/#downloadmanagerdownload_cfd)
- [`download_generation_data()`](/reference/rencal/core/rencalcoredata_downloader/#downloadmanagerdownload_generation_data)
- [`download_era5()`](/reference/rencal/core/rencalcoredata_downloader/#downloadmanagerdownload_era5)
- [`download_all()`](/reference/rencal/core/rencalcoredata_downloader/#downloadmanagerdownload_all)

[`download_all()`](/reference/rencal/core/rencalcoredata_downloader/#downloadmanagerdownload_all) enforces dependency order:

1. CfD register + BMU mapping,
2. generation data (depends on BMUs from CfD data),
3. ERA5 weather data.

## Downloader vs loader boundary

The two modules are complementary:

- **Downloader layer** ([`rencal.core.data_downloader`](/reference/rencal/core/rencalcoredata_downloader/)): fetches and writes raw/normalized artifacts.
- **Loader layer** ([`rencal.core.data_loader`](/reference/rencal/core/rencalcoredata_loader/)): reads those artifacts and returns validated dataset models.

```text
External APIs/files -> DataDownloader -> local artifacts -> DataLoader -> DatasetModel objects
```

## Relationship to dataset models

The downloader does not directly instantiate model classes, but it produces the files consumed by the loader methods that return:

- [`PlantDatasetModel`](/reference/rencal/models/rencalmodelsplant_model/#plantdatasetmodel)
- [`GenerationDatasetModel`](/reference/rencal/models/rencalmodelsgeneration_model/#generationdatasetmodel)
- [`ERA5DatasetModel`](/reference/rencal/models/rencalmodelsera5_model/#era5datasetmodel)

For model-layer details and validation behavior, see [Dataset Models](/concepts/rencal/models/dataset_models/).

## Operational notes

- **Credentials:** ERA5 requires a valid `CDS_API_KEY` (or explicit `api_key`).
- **Idempotence:** existing outputs are reused/skipped where appropriate.
- **Temporal correctness:** generation conversion logic accounts for UK settlement-day DST behavior before UTC aggregation.
